# U10b-0: Progression Rank From Training — phase index

**Spec:** `docs/superpowers/specs/2026-08-21-u10b-0-progression-rank-from-training-design.md`
— **read sections 13 and 14 first.** They supersede 1–12 where they conflict,
and sections 1–12 contain statements known to be false.

**Why phases.** Three monolithic plan versions (v1 `d2382b16a`, v2 `224222ba8`,
v3 `ede78aea1`) each failed a blind adversarial review. The findings were real
every time and moved outward each round — arithmetic, then Go blast radius, then
the 641 content files. The lesson is not that the reviews were too harsh; it is
that **this slice is too large to plan correctly in one document**, because each
part's discovered facts change the next part's design.

So it ships in phases. Each phase is independently shippable, independently
reviewable, and leaves the game in a working state. Later phases are planned
**after** their predecessor lands, not before — planning six phases in detail up
front is what produced the three failed versions.

The v3 monolith is preserved at commit `ede78aea1`. Its task bodies are the
starting point for phases B–F, **with the corrections listed under each phase
below applied**. Do not lift them unchanged.

## Phase A — Groundwork (no progression behaviour change)

**Plan:** `2026-08-21-u10b-0-phase-a-groundwork.md`

Value-neutral by construction and independently verifiable. Nothing here changes
how anything progresses.

- `GetStatTraining` accessor.
- `StatPoolTotal()` — names the concept four systems open-code, and returns the
  same number before and after the pool move, so those systems never see it.
- **Fold authored mob `training:` into `base:` across 599 templates.** The
  approved design assumed a mob's `Training` came only from the runtime stat-pool
  distribution. It does not: 599 of 641 mob files author `training:` directly,
  up to 188. Without this fold, `MobStatTrainingCap` would freeze the ~15 mobs
  whose authored value already exceeds it, at spawn.
- Re-point the mob web editor at `Base`.

**Ships:** nothing player-visible. Gate is a boot test plus `assess` / `raise` /
`charm` behaving identically.

**✅ SHIPPED 2026-08-22** — PR #55, merge `1c5d10fd7`. All gates green on master
(`lint`, `test`, `javascript`, `build`). Three things worth carrying forward:

- The adversarial playtest found a real bug in this phase's own accepted
  behaviour change: `assess` advertised undead forms on a player corpse that
  `raise` always refuses, because `selectRaiseCorpse` skips `UserId != 0` and
  `assess` had no such guard. Pre-existing, but the phase made it common. Fixed
  in the same PR.
- **Phase C owes an instance-save migration.** The mob-instance and companion
  restores *assign* `Training = saved value`, so a save written before the fold
  double-counts the authored portion. Measured: 265 of 266 local mob instance
  saves and 3 user saves are exposed. Prod carries no mob instance saves, but
  user saves do carry companions.
- `internal/mobs/statdump_test.go` is the value-neutrality harness this phase
  used (skips unless `MOB_STAT_DUMP` is set). Phase C should prove the
  spawn-pool move the same way: dump before, dump after, diff.

Two facts the plan had wrong, both found by executing: authored training runs
−188 to 100000 rather than "up to 188", and six templates author stats in YAML
flow style (`strength:    {training: 35}`), which an anchored regex silently
passes. Owner ruled that the two stats folding to exactly zero be handled by
fixing the hydration guard (`stats.StatInfo.BaseAuthored`) rather than fudging
the data.

The "spec correction owed" item is **closed**: spec section 15 already records
the authored-`training:` discovery.

## Phase B — Safety fixes (independently valuable)

Two live production bugs that do not depend on the re-key. Worth shipping even
if the rest of the arc stalls.

- **Kill the truncation.** `int(chance * 10000)` seals any stat whose chance
  drops below 0.01%; two of a live character's stats are dead in production
  today. Roll resolution to 1,000,000 plus `ProgressionChanceFloor`, applied to
  the two rank-driven sites only — **not** to `CheckRegenProgression`, whose
  chance is deliberately proportional to depletion and is supposed to vanish
  (spec 14.5).
- **`OnRegenTick` derives its own effective pool** so the reserved-pool faucet
  cannot be reopened by a future caller (spec 14.3).

**Corrections to the v3 bodies:**
- The pool reader is **`PoolValue`** (`internal/characters/pools.go:242`). There
  is no `GetPool`. v3's locating grep matched only `poolMax`, the *ceiling* —
  following it literally disables regen progression entirely.
- **`EffectivePoolMax` is floored at 1 and never returns 0**
  (`pools.go:313-318`). At ≥100% reservation the current call sites yield
  `max <= 0` and return early; naively swapping in `EffectivePoolMax` gives
  `max = 1, current = 0, ratio = 0` — *maximum* chance forever. Handle the
  fully-reserved case explicitly.
- v3's Task 4 fixtures used `Base = 40` claiming immunity from the old value
  floor. The floor is `Base + Training + Mods > softCap`, so it fires from
  `Training = 11` onward. Either run these tests after the re-key or keep
  `softCap` at 150 in them.

## Phase C — The re-key

The actual U10b-0 change. **Atomic**: all four rank sites plus both config
values plus both Go defaults in one commit. Any intermediate state where
`StatProgressionSoftCap` is 50 while a site still reads the counter fires the old
value floor for every stat on every character.

- Four rank sites: the skill block, the stat chance, the debug-log duplicate,
  and `regenDamperFactor`.
- Mob spawn pool `Training++` → `Base++`, save-schema changes, and the instance
  and companion migrations.
- `MobStatTrainingCap` 50, `MobSkillSoftCap` 20, `MobSkillTrainingCap` 25.

**Corrections to the v3 bodies:**
- **The pool distribution runs before `Validate()`** (`mobs.go:573-587`), and
  hydration only fires when `Base == 0`. Changing `.Training++` → `.Base++`
  therefore suppresses species hydration for exactly the stats that received
  points, on any path whose template was not already Validated. Move the
  distribution after `Validate()`, or force hydration first.
- **Both migrations double-count as v3 specified them.** Companions respawn via
  `NewMobByIdFresh`, which skips the instance load, so the fresh pool
  distribution *runs* and the saved pool is then added on top — every existing
  pet roughly doubles. The mob-instance branch has the same shape plus a second
  error: `Training` is not 0 there, because the template copy carries the
  authored YAML value (which Phase A has by then folded into `Base`, changing
  the arithmetic again). Re-derive both against post-Phase-A reality.
- v3's `hasProgression` reasoning is inverted, and after the move **44 mob types**
  (a `statpool` but no authored training, skills or mutations) drop out of it, so
  their rolled `Base` distribution stops persisting and re-randomises each spawn.
- `MobSkillCap 3 → MobSkillTrainingCap 25` is an 8× ceiling raise, not just a
  cap repair: rank 3 → 25 moves the damage multiplier 1.49× → 2.41× and the
  contest contribution +15 → +125. Model it before shipping.

## Phase D — Balance

- Fix `ProgressionDecayBelowCap` / `AboveCap` for curve **shape** only.
- Solve the per-stat and per-skill multipliers for **pace** (spec 14.2).
- Retune vitality against the **regen** faucet, damper included.
- Set `ObservedCritProgressionBonus` explicitly — absent means 0, which is why
  the crit path is dead for everyone today.

**Corrections to the v3 bodies:**
- v3's multiplier formula double-applies the old multiplier — silent at
  `m = 1.0`, 5× wrong for strength, and in the direction that pulls the
  truncation death point back down. Correct form:
  `m_new = usesToReach_new_at_m=1(T) / usesToReach_old(T)`.
- `CheckRegenProgression` also applies the per-stat multiplier, so solving
  strength/vitality/willpower/charisma against combat firing rates simultaneously
  rescales the regen faucet for those stats. v3 flagged this coupling for
  vitality only.
- The old-model formulas in v3 Task 9 Step 1 were verified correct against all
  four spec reference figures — keep them.

## Standing rules for every phase

1. **No absolute line numbers for code an earlier task shifts.** Locate with
   `grep` at execution time — and verify the grep matches the symbol you mean.
   v3's `GetPool` grep matched `poolMax` instead.
2. **Go defaults move with shipped values.** A test binary never loads
   `config.yaml`.
3. **Safety defaults use `<= 0`; only genuine off-switches use `< 0`.** The
   `< 0` idiom is why `ObservedCritProgressionBonus` sits at 0 in production.
4. **`characters.New()` calls `Validate()`**, which populates `Value` and
   hydrates `Base`. A disk-loaded fixture must be a raw
   `&characters.Character{}`.
5. **Migrations must never assign `Base`** without accounting for species
   hydration and for whether a fresh pool has already been rolled.
6. **A soft cap bounds nothing** — the curve never reaches zero and the floor
   guarantees it. Hard caps are separate knobs.
7. **`grep --include=*.go` cannot see `config.yaml`, `AGENTS.md`, or the 641 mob
   files.** Every prior round was bitten by this.
