# PR #208 review: craft gather hunt, security lens

Blind reviewer `craft_gather_hunt:security`, run 2026-10-05 against PR head `3ce674451`. Findings were then checked by independent verifiers (three for critical and high, one otherwise). Severity is the verifiers' median. Back to the [synthesized report](../README.md).

## Reviewer summary

I reviewed the wilderness trades phases 0-3 piece (skin/butcher/harvest, gather roll, quality grades, spoilage, tool recipes, shop graded value) with a security lens, reading the code at the PR head. I found four issues worth reporting. (1) Companion and mob corpse salvage still runs the old salvage table and ignores the new Skinned/Butchered state, so a carcass a player has only partly worked gets paid out twice. (2) Two same-mob corpses that died in the same round are told apart differently at the start and at the end of a job. A player can skin or butcher someone else's kill inside that player's loot window, and the true owner is locked out of their own carcass. (3) Spoilage, the economic sink for harvested raw goods, can be skipped completely: bank storage is never swept, and crafting (including the automatic pull from storage) never checks whether an input has rotted. (4) The craft grade cap ("one grade above the worst graded input") ignores ungraded inputs. Ungraded inputs, including graded goods laundered through a shop (shops restock by ItemId and drop Quality and CraftedRound), let a tool recipe reach pristine (4.0x sell value) limited only by the tool's tier. I found no injection, path traversal, external API or DoS issue in this piece. Player text only goes back to the player who typed it, and the spoilage sweeps are bounded per user.

### F046 [medium] Same-round twin corpses: harvest job resolves on a different corpse than the one ownership was checked on

`internal/actions/harvest.go:298` · status **confirmed** · reported as medium

startCarcassJob identifies the target with room.FindCorpse(name), which walks corpses newest-first and keeps the newest of each name (rooms.go:1486-1506). It checks LootAllowed on that corpse and keys the job only by MobId and RoundCreated. ResolveHarvest walks room.Corpses oldest-first and takes the first MobId+RoundCreated match. When two corpses of the same mob template die in the same round (an AoE, or two players fighting side by side), the corpse whose ownership was checked is the newest, but the corpse that gets worked is the oldest. The AI companion code already knows about this twin collision and refuses it (salvageHits, finds.go:156-170). The harvest path does not.

**Failure scenario.** Wolves W1 (killed by player A, OwnerUserIds=[A]) and W2 (killed by B, OwnerUserIds=[B]) die in the same round in one room; W1 is older. B types `skin wolf`. FindCorpse returns W2 (newest), LootAllowed(B) passes, and the job key is wolfId:round. On completion ResolveHarvest matches W1 first and skins A's kill inside A's loot window, so B gets A's pelt. When A types `skin wolf`, FindCorpse again returns W2, so A gets "That kill isn't yours to work yet" on their own carcass. Once W1 is Skinned, any later job on W2 also lands on W1 ("nothing left"), so W2 cannot be skinned until W1 is removed.

**Existing mechanism.** modules/aicompanion/finds.go salvageHits (twin detection). Better still, use a unique corpse identity: FindCorpseIndex already exists in rooms.go:1533.

**Suggested fix.** Make the job key unique to the corpse, for example by adding the owner or index, or by refusing twins as salvageHits does. Re-check LootAllowed for the actor in ResolveHarvest against the corpse actually found.

### F047 [medium] Companion/mob corpse salvage double-dips partly worked carcasses (skin, then companion salvage)

`internal/actions/salvage.go:138` · status **confirmed** · reported as high

The player `salvage` command refuses any corpse that has a harvest table (usercommands/salvage.go:160-168). The shared actions.salvageCorpse that mobs and the AI companion use was not given that rule. Its only eligibility test is `len(crafting.LookupCorpseSalvageForMob(...)) > 0`. It never checks CarcassTable, corpse.Skinned, corpse.Butchered or HarvestedParts. The companion's butcherable() (modules/aicompanion/finds.go:123-149) checks the same legacy table and also ignores carcass state. ResolveHarvest removes a corpse only when it is Spent (skinned AND butchered) with no loot (harvest.go:442). A carcass that has been skinned, or had one part harvested, therefore stays in the room, and the legacy salvage path pays its full table out again (raw-meat x1, leather-strip x2, sinew x1 for animal/canine/etc.).

**Failure scenario.** A player kills a canine. They run `skin wolf` and receive the species pelt(s); the corpse is now Skinned but not Butchered, so it stays. They then tell their AI companion to butcher/salvage the body: actions.go:542 butcherable passes and issues `salvage <mobId>:<round>`. Alternatively the companion's idle butcher pastime (finds.go:184) picks it up. mobcommands.Salvage leads to actions.salvageCorpse, which pays raw meat, 2 leather strips and sinew on top of the pelt. The same happens after a single `harvest fang from wolf`: the fang is taken, then the whole carcass is salvaged. Any NPC salvager mob running bare `salvage` (first eligible) also consumes fresh harvest-table carcasses under the old rules. That is inconsistent with the player path and gives a second source of the same materials.

**Existing mechanism.** actions.CarcassTable / SectionEntries (the new carcass state). The refusal belongs in actions.salvageCorpse, the one shared resolver, not only in the player command wrapper.

**Suggested fix.** In actions.salvageCorpse, skip any corpse whose CarcassTable is non-empty, or at least any with Skinned/Butchered/HarvestedParts set. Make butcherable() apply the same rule, so the companion and NPC salvagers follow the player rule. If companions should still butcher game, route them through ResolveHarvest instead.

### F048 [medium] Spoilage sink fully bypassable: bank storage never rots and crafting consumes spoiled goods (including auto-pull from storage)

`internal/hooks/spoilage.go:29` · status **confirmed** · reported as medium

Spoilage is the only sink on harvested raw goods. The only places that act on IsSpoiled are the player sweep (Items and ComponentItems only, every 10 rounds), the room floor/stash sweep, and the shop buy refusal (buyrules.go:84). The sweep says "Goods in bank storage are not swept: storage is a cold store", and house/room containers are explicitly skipped (rooms/spoilage.go:16-18). Nothing in crafting checks IsSpoiled: grepping IsSpoiled/Spoils() across the repo finds no hit in internal/crafting or the craft paths. ensureComponentsFromStorage → crafting.PlanStoragePull draws banked items straight into a craft. Processing "stops the clock" by producing a non-spoiling item (comment in items/spoilage.go:17-18).

**Failure scenario.** A hunter butchers in bulk and banks the raw meat or hides indefinitely; they never rot in storage. Weeks later they run `craft <jerky/cure-hide recipe>` at the right station. ensureComponentsFromStorage pulls the rotten meat from the bank and the craft consumes it, producing a non-spoiling output that sells normally. The same works by carrying rotten goods into the up-to-10-round gap before the per-user sweep (now%10 == userId%10), or by keeping them in a house chest. The intended pressure to process quickly does not apply.

**Existing mechanism.** items.Item.IsSpoiled, which already exists. It should be checked in crafting.SelectIngredients/HasIngredients/PlanStoragePull, the single ingredient selector.

**Suggested fix.** Treat spoiled items as absent in crafting's ingredient selection, including PlanStoragePull. Either sweep storage and containers lazily on access, or have the spoilage check consult IsSpoiled at use time wherever an item is consumed or valued.

### F133 [medium] Craft grade cap ignores ungraded inputs; shop resale strips grade, so a crude-input cap can be laundered

`internal/gather/gather.go:268` · status **refuted** · reported as medium

CraftGradeOutput computes `worst` only over inputs with a Valid() grade and caps the output at worst+1. An ungraded (QualityNone) input contributes nothing to that cap. When the recipe has a tool, an all-ungraded input set is graded standard-and-up and capped only by the tool tier, up to pristine with a masterwork tool. That is 4.0x sell value (config.yaml QualityValuePristine: 4.0), against inputs that price at 1.0x. Ungraded inputs are easy to get: shops restock by ItemId only (AddStockAtRound(item.ItemId, 1, ...) in sell.go), so a crude hide sold to a shop is resold ungraded with CraftedRound 0. Legacy corpse salvage (humanoids, and the companion path above) and forage also yield ungraded materials. The comment's stated invariant ("a pristine output cannot be made from crude hides") therefore does not hold.

**Failure scenario.** A player harvests crude hides (cheap tool, poor roll), sells them to a tanner and buys the same units back ungraded. The shop's AddStockAtRound drops Quality and CraftedRound, which also resets the spoilage clock. They then run a tool recipe such as cure-hide (tool: scraper). With all graded inputs gone, worst == QualityNone, so the output reaches the tool tier's MaxGrade instead of standard (crude+1). Mixing ungraded and graded inputs also raises the cap to the worst *graded* input, not the actual worst.

**Suggested fix.** When any consumed input is ungraded, treat it as QualityStandard for the cap. At minimum, cap tool-only grading of ungraded inputs at standard+1. Have shop stock either keep the grade or refuse to resell graded/stamped walk-in goods as fresh ungraded stock.
