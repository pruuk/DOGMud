# PR #208 review: lively api, unification lens

Blind reviewer `lively_api:unification`, run 2026-10-05 against PR head `3ce674451`. Findings were then checked by independent verifiers (three for critical and high, one otherwise). Severity is the verifiers' median. Back to the [synthesized report](../README.md).

## Reviewer summary

Unification/reuse review of the "livelier world" piece (internal/lively, npcidle, roomlife, lookdetail, the matching modules, and the apiframework/aicompanion relay changes), judged at the PR head. The most serious finding comes straight from skipping an existing mechanism. Baseline already has an allowlist for text written on a player's own key and read by other players: baubles.CheckPlayerKeyText, owner ruling 15. The new features instead wrote their own looser blocklist, which lets ';' through. npcidle then acts the moment as a mob command string (mob.Command(kind+" "+text)), and Mob.Command splits on ';'. Anyone who controls the reply through the relay can therefore run any mob command: givequest, give gold, broadcast, attack. That is critical. Second, lively.Moderate is described as "the baubles policy" but differs from the baubles moderate() it copies: with ModerateOutput off it shows player-key text to everyone, where the baubles rule (2026-09-29) keeps it to the finder. On top of that, none of the new moderation knobs were added to configs.hardLocked (ruling 13), so an in-game admin can turn moderation off. Third, the consent default for the "Make the world livelier" box is the reverse of the existing "finds" box. It starts ticked, and keys saved before this feature existed are silently opted in. Fourth, the requests list every NPC in the room, including hidden ones, without using Character.Perceives, so a hidden NPC's name can turn up in text shown to the whole room. Fifth, lively.Ask and lively.Moderate are near-verbatim copies of baubles viaPlayer and moderate, and baubles was not moved onto them. The delivery and module scaffolding is also copied three times, which leaves several copies to drift. Done well: the shared apiframework spending path is reused throughout (Reserve/Settle/Charged/Allowance/DecodeChat/EstimateTokens/StatusError). The relay is reused with a per-purpose breaker table (relayOwner.lent) instead of a parallel relay. Model text goes through baubles.PlainText and items.Item.ModelName. Sight checks use messaging.CanSeeClearly/ParticipantSight and the room's own senders (SendTextVisual, SendTextVisualHidingNames). The keyholder-only emote reuses actions.FormatEmoteText. lookdetail is added after actions.ResolveLook's sight rules instead of redoing them. Spending caps reuse apiframework's per-user allowance dimensions instead of new counters. The idle hooks call into the existing idle paths instead of adding a new tick.

### F003 [critical] Player-key idle moment injects arbitrary mob commands via ';' (bypasses the ruling-15 player-key allowlist)

`internal/npcidle/npcidle.go:290` · status **confirmed** · reported as critical

A generated idle moment is acted by building a command string and passing it to Mob.Command, which splits its input on ';' and queues each piece as its own mob command. npcidle.CleanResult only blocks control and non-ASCII characters plus < > ` \, so ';' (and digits, ':' and '/') pass. The reply content comes through the player's own browser relay, which the player controls: the code itself says so (lively.go: 'The count came through the player's browser, which they can write'). The set-line path already knows about this: IsFlavor refuses any set command containing ';'. The generated path does not. Baseline already has the right tool for text written on a player's key and read by others, baubles.CheckPlayerKeyText (internal/baubles/playerkey.go, `^[A-Za-z ',.!?"-]*$`, ruling 15), which specifically refuses semicolons. The safe delivery helpers (actions.Say / actions.FormatEmoteText, the latter already used by sendToKeyholder) avoid command parsing entirely.

**Failure scenario.** A player has a relay up with lively ticked and stands in a room with an idle NPC. The server has a key and moderation works, or ModerateOutput is off. Their modified relay page answers the npc_idle request with {"kind":"emote","text":"nods slowly;givequest 12-end;give 500 gold bob"}. CleanResult accepts it: printable ASCII, contains a space, no 'you'. A content moderation model will not flag it. finish() runs mob.Command("emote nods slowly;givequest 12-end;give 500 gold bob"), so the NPC emotes, then raises a quest-completion event for every player in the room and hands over its gold. Commands like broadcast, attack, portal and despawn can be reached the same way.

**Existing mechanism.** internal/baubles/playerkey.go baubles.CheckPlayerKeyText / playerKeyTextRE (ruling 15); internal/actions/say.go actions.Say and internal/actions/emote.go actions.FormatEmoteText for delivering a line without command parsing

**Suggested fix.** Hold all player-key lively text to the existing playerKeyTextRE allowlist: generalize CheckPlayerKeyText to take strings and call it from every lively CleanResult. Act the moment through actions.Say / an emote body built with FormatEmoteText plus the room sender instead of mob.Command(string). At minimum, refuse ';' in CleanResult.

**Suggested fix.** Extract the ruling-15 check into a string-level helper (in baubles or apiframework) and apply it in each lively CleanResult, replacing the three copied blocklists.

`modules/aicompanion/relayweb/relay.js:185` · status **confirmed** · reported as high

**Existing mechanism.** The finds permission in modules/aicompanion/relayweb/relay.js and relay-setup.html (opt-in, absent = false), relayOwner.finds in tiers.go

**Suggested fix.** Follow the finds pattern: unticked by default, `lively: s.lively === true` for sealed and legacy settings, so existing key holders must opt in.
