# PR #208 review: rifts, security lens

Blind reviewer `rifts:security`, run 2026-10-05 against PR head `3ce674451`. Findings were then checked by independent verifiers (three for critical and high, one otherwise). Severity is the verifiers' median. Back to the [synthesized report](../README.md).

## Reviewer summary

Security review of the rift framework commit (a4f372715), checked against the PR head. The main problem is in the generated-room path. A rift room "written by a model" is really whatever JSON the player's own browser relay sends back. The game treats that as trusted, saves it as a permanent world file and shows it to every later visitor. Nothing records which player wrote it, and the only content check is a harm-category moderation pass, which does not catch phishing or fake staff notices. The consent model is reused correctly: the relay's purpose check, lively.Turns/Ask/Moderate and apiframework's per-purpose allowances. The problem is scope: the existing "Make the world livelier" box, which is ticked by default, now also covers a far more expensive feature that saves its output for everyone, and the consent text was not updated. On reuse, the routing hooks (AddExitRouter/AddEntryGuard), owned chunks, forager overlay, bauble delivery and lively all extend existing mechanisms rather than duplicating them. Several paths hold up under review: rift-only item purge, entry guard and party joins, the fold anchor and recall gates, the file-name slug, and boot tolerance of bad generated files. One low-severity issue: a server crash at the wrong moment can duplicate items through the lost-items record.

### F041 [medium] Player-forged relay replies become permanent world rooms shown to every rift visitor, with no record of who wrote them

`modules/rifts/gen.go:102` · status **confirmed** · reported as high

The generated-room path runs the model call through the player's own browser relay. It then treats the reply as model output and saves it permanently. The player controls that reply completely. The codebase already says so: callModelOnce talks of 'a count relayed through a player's browser, which that player can write', and relay.js isAllowedEndpoint accepts plain http on localhost, so a player can point the relay at their own server. The reply passes through ParseRoomReply and BuildGenerated (internal/rifts/gen.go:289, 401) and then lively.Moderate. addGenerated (gen.go:827-866) then writes it to <DataFiles>/rifts/rooms/<profile>/gen-*.yaml, adds it to the pool straight away, reloads it at every boot, and serves it to every later party that rolls that template. The checks limit structure and character set only. plainProse (gen.go:373-383) allows letters, digits, ':', '/', '.', '@', '?', '=' and '&', so URLs and email addresses pass. Moderation flags harm categories (hate, sexual, violence and similar), not phishing, advertising or staff impersonation. Compare the existing lively features: lookdetail keeps moderated text only in an in-memory LRU of 4096 entries (internal/lookdetail/lookdetail.go:39, 79) and never writes it to disk. This feature is the first to turn a player's relay output into permanent shared world data. The saved Template has no author field (internal/rifts/data.go:335-339: Model, PromptVersion and Created only). Neither the 'saved' log line (gen.go:809) nor the LogRequests line (modules/rifts/gen.go:131) records the userId. An operator therefore cannot find or bulk-remove one player's rooms. A player with alts can also seed many rooms, up to GenerateMaxPerPool=200 per pool, or no limit if the operator sets 0.

**Failure scenario.** A player ticks 'Make the world livelier', points their relay at http://localhost:8080 (or edits relay.js in the browser), and enters a rift. When maybeGenerate reserves their turn (25% of rooms built, every 300s), the forged server returns valid rift_room JSON. Its description is 120 to 260 plain words of in-world prose, plus text such as 'A notice is carved here from the keepers of this realm: your account is flagged, confirm it at dogmud-support.example/verify or by mail to keeper@example.com'. Every word limit, noun-mention rule and character check passes, and omni-moderation flags nothing. The room goes to disk as gen-c-<slug>.yaml and appears to every later rift party, permanently and across reboots. The operator cannot tell which account wrote it.

**Existing mechanism.** internal/lookdetail keeps player-key output in memory only (lru cache, lookdetail.go:79). The keyholderOnly/moderation policy in internal/lively covers display, not permanent banking.

**Suggested fix.** Do not treat relayed output as trusted for permanent shared content. Options: (a) put generated rooms in a review queue an admin must approve before they join the pool (for example, write them to a pending/ directory); (b) at minimum, record the author userId and character name on the Template and in the save log, add an admin 'rift gen purge <user>' command, and reject URL, email and domain patterns in plainProse; (c) generate on the server's key only, so the output is not controlled by the client.

### F096 [low] A crash after a rift death or logout can duplicate items: the lost-items record is written to disk at once but the player save is not

`internal/rifts/lost.go:174` · status **confirmed** · reported as low

forfeit removes items from the in-memory character and appends copies to lostItems. lostChanged() then calls modules/rifts saveLost, which writes the plugin state straight away (modules/rifts/rifts.go:149-154). The character file is not saved at that point; it is saved later by autosave or on leave. If the process dies in between (a crash, OOM kill or SIGKILL on the 961 MB droplet), the player reloads with every forfeited item still in their file, and the restored lost record holds copies that rubble searches hand to whoever finds them. findLost has the reverse problem: it removes the item from the record and saves at once, before the finder is saved, so an item can vanish from both. Players cannot cause a crash, so this is not an on-demand exploit, but it is a crash-timed save hazard.

**Failure scenario.** A player dies in a rift carrying a valuable weapon. forfeit takes it and saveLost writes it to lost-items. The server is OOM-killed before the next user autosave. On restart the player's save still holds the weapon, and lost-items also holds it. An alt's later rubble search (find_chance) can turn up the second copy.

**Suggested fix.** Save the user record in the same step as saveLost (or before it) when items move between a character and the lost record. Alternatively, mark lost-record entries pending until the owner's next successful save.

### F097 [low] The existing 'Make the world livelier' consent, ticked by default, silently extends to a far more expensive feature whose output is saved for everyone

`modules/rifts/files/data-overlays/config.yaml:45` · status **confirmed** · reported as medium

Rift room writing is a new lively purpose (apiframework.PurposeRifts = 'lively:rifts'). It passes the relay's consent check only because IsLively matches the 'lively:' prefix. Every player who already ticked the single 'Make the world livelier' box is now enrolled. That box is checked by default on the key page (relay-setup.html:44: `<input id="lively" type="checkbox" checked>`). Its wording, 'now and then, the world around me comes up with something new of its own', was not changed by this commit and does not say that the key will write rooms saved to the server for other players. Cost is also much higher than the features the player agreed to. GenerateEnabled defaults to true. GenerateDailyTokensPerUser is 40000, against 20000 for npcidle, roomlife and lookdetail in _datafiles/config.yaml. GenerateMaxCompletionTokens is 4000 per call, against 600 to 800 for the others. Allowances are per feature and add up, so a consenting player's worst-case daily spend on their own key rises from about 60k to about 100k tokens with no new opt-in. Rooms are also written on the key of a random run member (memberIdsShuffled), so a party member's movement spends a different player's key.

**Failure scenario.** A player set up their key months ago for the companion and left the default-ticked lively box on. After this PR they join a friend's rift party. The friend walks the rooms, each one triggers maybeGenerate at 25%, and the shuffled member selection picks the quiet player's key. Each call can use up to 4000 completion tokens (a reasoning model's thinking counts) plus a prompt carrying three example rooms. The player is billed for up to 40000 extra tokens a day, for content they never knowingly agreed to write for other people, and nothing on the key page tells them.

**Existing mechanism.** apiframework per-purpose consent (o.allows(purpose)) and the key page's separate 'finds' checkbox show how to add a distinct opt-in for a feature of a different kind.

**Suggested fix.** Give rift room writing its own key-page checkbox, unchecked by default, that says the output is saved to the world for other players. Alternatively, have relayTable.allows refuse PurposeRifts unless the owner has opted in to that purpose specifically. Bring the token defaults in line with the other lively features, or say on the key page what this feature costs.
