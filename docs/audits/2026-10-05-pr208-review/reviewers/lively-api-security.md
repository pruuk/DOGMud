# PR #208 review: lively api, security lens

Blind reviewer `lively_api:security`, run 2026-10-05 against PR head `3ce674451`. Findings were then checked by independent verifiers (three for critical and high, one otherwise). Severity is the verifiers' median. Back to the [synthesized report](../README.md).

## Reviewer summary

Security review of the "livelier world" piece (lively, npcidle, roomlife, lookdetail, plus the apiframework and aicompanion relay changes). The key fact is that every "model reply" reaches the server as a Companion.Relay.Response GMCP message from the keyholder's own client. The server sends the Request id to that same client, and deliver() only checks that the id and owner match. A malicious keyholder can therefore return any text they like. They do not need prompt injection or a real provider.

Critical: npcidle passes that text to mob.Command(kind + " " + text). Mob.Command splits on ';', and CleanResult does not reject ';'. So a forged idle moment makes a townsfolk NPC run any mob command: give its gold or items to an alt, attack another player, suicide (death, loot drop), "suicide vanish" (permanent despawn), or broadcast server-wide. With shipped config (ModerateOutput true) this works whenever the server has a key, because moderation only checks content for harm. It also works when moderation is off. The trigger is passive: the attacker stands near the NPC with the lively box ticked (default) and answers when an idle request arrives.

Medium: lookdetail puts player-forged text into a global per-room cache, and everyone who later looks at that thing reads it as authoritative room description. roomlife broadcasts forged text to the whole room as an ambient line. The only gate on either is the toxicity moderation check.

### F002 [critical] Forged npcidle reply injects arbitrary mob commands via ';' (gold/item transfer, NPC kill/despawn, PvP attack)

`internal/npcidle/npcidle.go:290` · status **confirmed** · reported as critical

An idle moment's text goes to mob.Command(res.Kind + ` ` + res.Text). Mob.Command (internal/mobs/mobs.go:978) runs strings.Split(inputTxt, `;`) and queues each piece as its own mob command. CleanResult (internal/npcidle/reply.go:395-399) only rejects control characters, non-ASCII, < > ` and backslash, so ';' gets through. The reply text is fully attacker-controlled. lively.Ask sends the request through the keyholder's own client relay. The server sends Companion.Relay.Request with its id to that same client, and onRelayInbound/pendingRelays.deliver (modules/aicompanion/relay.go:155-170) accepts any Companion.Relay.Response whose id and owner match. A player can answer by sending their own GMCP or by pointing the key page's endpoint at a server they run. Moderation (lively.Moderate) is a toxicity classifier and will not flag 'say Good day;give 300 gold alt'. With no server key the result is KeyholderOnly and goes through sendToKeyholder (safe). With a server key and ModerateOutput true (shipped), or with ModerateOutput false, it reaches mob.Command. Excluded() only skips companions and charmed mobs, so merchants, guards and quest givers are all eligible.

**Failure scenario.** Setup: the server has a key (normal when the companion runs on it), and npcidle is Enabled with ModerateOutput true (shipped config). The attacker ticks 'Make the world livelier' (the default) and stands in a room with a townsfolk NPC that has an idle say or emote. With Chance 5 they eventually receive an npc_idle Companion.Relay.Request. They answer with status 200 and a body whose choices[0].message.content is {"kind":"say","text":"Fine weather;give 500 gold bob"}. CleanResult passes it, moderation does not flag it, and finish runs mob.Command("say Fine weather;give 500 gold bob"). The NPC says the line and then gives its gold to the attacker's alt bob (mobcommands.Give). Other payloads: ';attack <victim>' makes a guard attack another player; ';suicide' kills the NPC so its loot drops (repeatable on every respawn); ';suicide vanish' runs DeleteMobInstance and despawns a quest giver; ';broadcast <spam>' posts server-wide in the NPC's name. The 30 s MinSecondsPerPlayer and the 20000-token daily allowance are the only limits, and the forged reply sets its own token count.

**Existing mechanism.** The mobs' emote/say mob commands can be dispatched as a single command without going through the ';'-splitting Mob.Command. The repo's own IsFlavor (npcidle.go:135) already treats ';' as unsafe for the input side but not for the output side.

**Suggested fix.** Reject ';' (and any other command separator) in CleanResult for both kinds. Better, do not build a command string from model text at all: call the say/emote handler directly with the text as its argument, or queue a single events.Input that is not split. Add a test where text containing ';give' is refused or acted as plain speech.

### F036 [medium] lookdetail caches player-forged text globally as authoritative room description for every later looker

`internal/lookdetail/lookdetail.go:218` · status **confirmed** · reported as medium

A closer look is written on the looker's own key through the client relay, so the reply is whatever the looker's client sends (see the npcidle finding). In finish, when the result is not KeyholderOnly (moderation passed, or ModerateOutput is false), cache.Add(d.key, res.Text) stores it under room id + description hash + phrase. TryLook (line 141) then serves it to every player who looks at that phrase in that room, with no further key involved. It lasts until the LRU evicts it (4096 entries), the description changes, or the server restarts. CleanResult allows up to 700 characters of plain ASCII. The only gate is the moderation endpoint, which checks for harmful content, not authenticity. One attacker can therefore cheaply fill every described noun with fake hints, false directions, scam text ('the plaque reads: the guildmaster pays double for gold given to Bob'), or text that looks like a system message, all presented in the room-noun format the look command uses for authored content.

**Failure scenario.** The attacker walks the town looking at nouns from each room description ('look fountain', 'look plaque'), with MinSecondsPerPlayer 5. Each look sends them a look_detail request, and they answer with crafted plain-ASCII text that passes omni-moderation. Every later player who types 'look fountain' in that room reads the attacker's text as the fountain's description, from the cache, at no cost to anyone, until restart or eviction.

**Suggested fix.** Do not cache a detail from one player's key for others. Alternatively, cache only after independent agreement or staff review, or limit the cache to the keyholder. At minimum, record the authoring userId with the cache entry so staff can purge one player's entries, and expose a purge command.

Two things limit the impact and keep this at medium rather than high: - The cache lives only in memory. - The phrase must appear in the room description. - The text cannot carry markup or ANSI codes, so it cannot imitate the coloured system lines; it can only be plain prose inside the look frame. - When a server key exists, moderation runs on it by default (ModerateOutput: true in config.yaml).

### F093 [low] roomlife broadcasts attacker-chosen narration to everyone in the room as an ambient line

`internal/roomlife/roomlife.go:272` · status **confirmed** · reported as low

Same trust gap as above. A roomlife event's text comes from the keyholder's client. After CleanResult and moderation it is sent to every player in the room (SendText for heard events, SendTextVisual for seen ones) in CategoryRoomDescription, so it is indistinguishable from authored ambient text. CleanResult blocks markup and 'you' outside the 'You hear' prefix. Third-person text such as 'You hear the town crier announce that the bank will pay double for gold handed to Bob at the gate' still passes. Messages are not cached, which limits the reach to whoever is present. The attacker can repeat it every MinSecondsPerPlayer (60 s) whenever the Chance roll picks them.

**Failure scenario.** A malicious keyholder idles in a busy hub room. Each time a room_event request arrives, they answer with a heard event carrying a scam or impersonation line. Every player in the hub reads it as world narration.

**Suggested fix.** Treat output from a player's key as player speech. Either keep it KeyholderOnly whenever other players are present, or label and log it with the authoring userId so moderation can act on reports.
